本文档定义“容器化日志收集平台”完整MVP的功能范围、质量要求、技术约束和验收方法，作为后续用例设计、架构设计、编码、测试和发布的共同基线。

本文档重点回答“系统必须提供什么能力，以及怎样判断能力已经完成”。具体包结构、类和函数设计、组件配置细节不在本文档中展开，统一放入架构设计、ADR和部署文档。

- `docs/implementation-plan.md`中已经确认的实施方案。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 日志事件 | 平台处理的最小日志单元，包含正文、级别、时间和来源元数据 |
| 来源服务 | 产生日志的逻辑应用，例如`log-producer` |
| 来源容器 | 实际产生日志的Docker容器实例 |
| 采集 | Filebeat从stdout、stderr或日志文件中读取新增事件的过程 |
| 传输 | Filebeat经Logstash把事件发送给Gin内部接收接口的过程 |
| 入库 | Gin完成校验、规范化和去重后，通过GORM写入SQLite的过程 |
| 幂等 | 同一事件被重复提交时，SQLite最终只保留一条记录 |
| registry | Filebeat保存文件身份和读取位置的持久化状态 |
| 持久队列 | Logstash用于在下游暂时不可用时保存待投递事件的磁盘队列 |
| 公开API | 用户或第三方服务可访问的查询、统计和健康检查接口 |
| 内部API | 仅供Compose内部日志传输链路调用的日志接收接口 |

## 2. 项目背景与目标

### 2.1 项目背景

单机日志工具只能分析用户主动指定的本地文件，无法自动收集容器运行期间持续产生的日志。项目二需要把日志处理能力升级为长期运行的容器化服务，形成“自动采集、可靠传输、分类存储、条件查询和统计分析”的最小闭环。

### 2.2 核心目标

平台必须实现：

1. 自动采集指定容器的stdout、stderr和NDJSON文件日志。
2. 为日志补充容器、服务、来源和时间等分类信息。
3. 通过Filebeat和Logstash把日志可靠发送给Go服务。
4. 通过Gin、GORM和SQLite完成日志校验、幂等存储和持久化。
5. 提供日志详情、组合查询、分页和统计REST API。
6. 通过Docker Compose一键启动完整平台。
7. 在约定故障场景和缓冲容量内实现最终无缺失、存储无重复。
8. 通过可重复的单元、集成、端到端和性能测试证明验收结果。

### 2.3 成功判定

项目只有在真实容器日志能够自动进入SQLite，并能通过公开API查出时，才算形成端到端闭环。以下情况不视为完成：

- Filebeat只把事件打印到控制台，没有进入SQLite。
- SQLite中的数据完全依赖人工调用POST接口创建。
- API只支持固定条件或返回硬编码数据。
- Compose启动后仍需要人工进入容器执行初始化命令。

## 3. 参与者

### 3.1 平台用户

通过REST API查询日志、查看单条详情和获取统计结果的人或第三方服务。

### 3.2 平台运维者

负责通过Docker Compose部署、启动、停止、升级和排查平台，查看各组件健康状态。

### 3.3 来源服务

产生日志并被平台采集的容器化应用。MVP使用`log-producer`作为可重复验收的标准来源服务。

### 3.4 内部组件

- `filebeat`：采集和补充来源元数据。
- `logstash`：接收Beats事件并通过HTTP批量转发。
- `api`：接收、校验、存储、查询和统计日志。
- SQLite：嵌入`api`进程的数据文件，不是独立容器服务。

## 5. 假设与技术约束

### 5.1 运行环境

- 开发和验收环境为WSL2 Ubuntu 24.04。
- 使用原生Docker Engine和Docker Compose v2命令`docker compose`。
- 项目代码保存在WSL的Linux文件系统中。
- 首次镜像拉取可能受网络环境影响，不计入服务启动时间。

### 5.2 技术栈约束

- Go版本不低于1.22。
- HTTP框架使用Gin。
- ORM使用GORM。
- 数据库使用SQLite。
- 日志采集使用Filebeat。
- 传输桥接使用Logstash。
- 多容器编排使用Docker Compose。
- 所有容器镜像必须固定明确版本，不得使用`latest`。

### 5.3 架构约束

- Compose必需服务为`api`、`filebeat`、`log-producer`和`logstash`。
- SQLite是`api`使用的嵌入式数据库文件，不创建SQLite容器。
- SQLite文件必须绑定挂载到仓库`./data`目录。
- Filebeat只能采集明确允许的目标容器和目录，必须排除自身及Logstash，避免递归采集。
- 内部日志接收入口不能直接暴露给宿主机外部用户。
- 公开查询API和内部接收API必须具有明确的访问边界。

### 5.4 数据约束

- 所有服务内部时间统一使用UTC。
- API时间参数和响应时间使用RFC3339格式。
- API必须为所有合法日志计算稳定的平台`event_id`；来源可以提供可选的`source_event_id`作为指纹输入。
- 日志级别统一转换为大写。
- 未识别或缺失的级别规范化为`UNKNOWN`，不得导致采集链路退出。
- 单条日志正文的初始上限为64 KiB；超限事件必须被明确拒绝或截断，并留下可排查记录。

## 6. 系统上下文

```text
log-producer
  ├─ stdout/stderr ─┐
  └─ NDJSON文件 ────┤
                    ↓
                 Filebeat
                    ↓ Beats
                 Logstash
                    ↓ HTTP JSON批次
                 Gin内部API
                    ↓ GORM
                  SQLite
                    ↑
             Gin查询与统计API
                    ↑
               平台用户
```

## 7. 功能需求

### FR-001：采集容器stdout日志

- 优先级：Must
- 描述：系统应采集被明确标记为目标服务的容器stdout日志。
- 前置条件：Compose平台已启动，`log-producer`被标记为允许采集的目标服务。
- 输入：`log-producer`写入stdout的日志行。
- 输出：进入传输链路的规范化日志事件，`source`为`stdout`。
- 验收：生成100条具有唯一编号的stdout日志，最终SQLite中能够查询到对应100条事件。

### FR-002：采集容器stderr日志

- 优先级：Must
- 描述：系统应采集被明确标记为目标服务的容器stderr日志，并与stdout来源区分。
- 前置条件：Compose平台已启动。
- 输入：`log-producer`写入stderr的日志行。
- 输出：进入传输链路的规范化日志事件，`source`为`stderr`。
- 验收：生成20条具有唯一编号的stderr日志，最终SQLite中能够查询到对应20条事件，且来源字段正确。

### FR-003：采集NDJSON文件日志

- 优先级：Must
- 描述：系统应持续采集`log-producer`写入共享目录的NDJSON文件新增内容。
- 前置条件：`producer-logs`共享卷已同时挂载到`log-producer`和Filebeat，Filebeat只读访问。
- 输入：一行一个JSON对象的NDJSON文件。
- 输出：进入传输链路的规范化日志事件，`source`为`file`。
- 验收：向文件追加100条合法事件后均能入库；追加一条非法JSON时，采集服务不中断并生成可排查的解析错误。

### FR-004：限制采集范围

- 优先级：Must
- 描述：系统只能采集明确允许的来源，不能默认采集所有Docker容器。
- 验收：`log-producer`日志能够进入平台；Filebeat、Logstash和API自身运行日志不会被同一采集链路再次采集。

### FR-005：补充并保留分类元数据

- 优先级：Must
- 描述：系统应为每条事件补充并保留容器名、容器ID、服务名、来源类型、日志级别和日志发生时间。
- 验收：从stdout、stderr和文件各抽查至少10条事件，相关字段与实际来源一致；不存在的可选字段使用空值，不伪造数据。

### FR-006：经Logstash传输日志

- 优先级：Must
- 描述：Filebeat应通过Beats协议把事件发送给Logstash，Logstash应通过HTTP把JSON事件批量发送给Gin内部接收接口。
- 验收：关闭Logstash时Filebeat显示重试状态；恢复Logstash后积压事件能够继续传输，且不需要重启整个平台。

### FR-007：接收单条和批量日志事件

- 优先级：Must
- 描述：Gin应提供内部单条和批量日志接收能力，批量接口是Logstash的主要目标入口。
- 接口基线：`POST /internal/v1/logs`和`POST /internal/v1/logs/bulk`。
- 验收：合法单条事件成功接收；合法批次返回接收数、插入数、重复数和拒绝数；空批次返回HTTP 400。

### FR-008：校验和规范化事件

- 优先级：Must
- 描述：系统在入库前应校验必要字段、时间和正文大小，并执行级别、时间和来源字段规范化。
- 验收：缺少正文、缺少时间、时间格式错误或正文超限时返回明确错误；一个非法请求不得导致API进程退出。

### FR-009：幂等存储日志

- 优先级：Must
- 描述：同一来源日志事件因重试被多次提交时，API应计算相同的平台`event_id`，SQLite最终只能保存一条记录。
- 验收：具有相同`source_event_id`和来源命名空间的事件连续提交10次，数据库中只存在一条记录；批量响应能够报告重复数量。

### FR-010：持久化SQLite数据

- 优先级：Must
- 描述：SQLite数据库文件应保存在仓库`./data`绑定挂载目录中。
- 验收：写入数据后删除并重建`api`容器，原有数据仍能查询；宿主机能够看到数据库文件。

### FR-011：组合查询日志列表

- 优先级：Must
- 描述：用户应能按容器名、服务名、级别、开始时间和结束时间任意组合查询日志。
- 接口基线：`GET /api/v1/logs`。
- 验收：单条件和多条件查询结果均正确；无匹配数据返回HTTP 200和空数组；开始时间晚于结束时间时返回HTTP 400。

### FR-012：查询单条日志详情

- 优先级：Must
- 描述：用户应能根据数据库ID查询一条日志的完整详情。
- 接口基线：`GET /api/v1/logs/:id`。
- 验收：存在的ID返回HTTP 200和完整字段；不存在或非法ID返回对应的HTTP 404或400。

### FR-013：分页和排序

- 优先级：Must
- 描述：日志列表必须支持分页，并默认按`logged_at`倒序、`id`倒序稳定排序。
- 规则：`page`默认1；`page_size`默认20、最大100。
- 验收：连续翻页时记录不遗漏、不重复；非法页码返回HTTP 400；超过最大值时按约定拒绝或限制并保持行为一致。

### FR-014：按级别统计

- 优先级：Must
- 描述：用户应能统计指定过滤范围内各日志级别的数量和占比。
- 接口基线：`GET /api/v1/stats/levels`。
- 验收：统计数量与数据库查询结果一致；非空结果占比之和允许因四舍五入存在不超过0.1%的误差；空数据返回空结果。

### FR-015：按服务统计

- 优先级：Must
- 描述：用户应能统计指定时间范围内各来源服务的日志数量。
- 接口基线：`GET /api/v1/stats/services`。
- 验收：统计数量与数据库查询结果一致，并支持进一步按容器或级别筛选。

### FR-016：提供健康和就绪状态

- 优先级：Must
- 描述：API应分别提供进程存活状态和依赖就绪状态。
- 接口基线：`GET /healthz`和`GET /readyz`。
- 验收：进程正常时`/healthz`返回HTTP 200；SQLite不可访问或初始化失败时`/readyz`不得返回HTTP 200。

### FR-017：Docker Compose一键部署

- 优先级：Must
- 描述：用户应能通过一条Compose命令构建并启动所有必需服务。
- 启动命令：`docker compose up -d --build`。
- 验收：无需进入容器执行额外初始化命令，最终所有必需服务达到约定健康状态，公开API可访问。

### FR-018：组件重启后自动恢复

- 优先级：Must
- 描述：`api`、Filebeat、Logstash或`log-producer`在单独重启后，应在无需人工修复状态文件的情况下恢复工作。
- 验收：分别重启组件后继续生成日志，平台最终能够入库新事件；已经确认的事件不产生重复存储。

### FR-019：输出结构化运行日志

- 优先级：Must
- 描述：API应输出JSON格式的结构化运行日志，记录请求方法、路径、状态码、耗时、事件类型和request ID。
- 验收：一次公开API请求的响应头、请求日志和相关错误日志具有相同request ID；默认不完整打印用户日志正文和敏感Header。

### FR-020：优雅停止API

- 优先级：Must
- 描述：API收到`SIGTERM`时应停止接收新请求，在配置的超时范围内完成正在处理的请求并关闭SQLite连接。
- 验收：在请求执行期间停止容器，服务按约定完成或超时取消请求，不出现数据库损坏，容器最终正常退出。

## 8. 非功能需求

### NFR-001：API启动时间

- 优先级：Must
- 要求：从`api`容器进程开始运行到`/readyz`首次返回HTTP 200不超过3秒。
- 测量边界：不包括镜像拉取和镜像构建；连续测量至少5次并记录结果。

### NFR-002：查询响应时间

- 优先级：Must
- 要求：在SQLite预置10,000条日志、10个并发客户端、持续30秒的条件下，容器名、级别和时间范围组合查询的p95响应时间不超过500ms。
- 报告要求：记录p50、p95、p99、错误率、硬件、WSL版本、Docker版本和测试命令。

### NFR-003：故障场景可靠性

- 优先级：Must
- 要求：在约定的缓冲容量、等待时间和标准故障注入流程内，最终缺失事件数为0、SQLite重复存储数为0。
- 说明：传输链路按至少一次处理，存储层通过幂等约束消除重试产生的重复。

### NFR-004：状态持久化

- 优先级：Must
- 要求：SQLite文件、Filebeat registry和Logstash持久队列分别使用持久化挂载；普通容器重建不能删除这些状态。
- 验收：执行逐组件重建测试后，数据和读取进度保持正确。

### NFR-005：测试质量

- 优先级：Must
- 要求：`go test ./...`全部通过；核心Go包语句覆盖率目标不低于80%。
- 覆盖范围：至少包括配置、校验、幂等键、repository、service、handler和ingestion逻辑。

### NFR-006：容器安全基线

- 优先级：Must
- 要求：API运行时使用非root用户；内部接收入口不公开映射；敏感配置不写入镜像和Git。
- 说明：Filebeat读取Docker日志和元数据所需的较高权限必须最小化，并在架构文档中记录风险。

### NFR-007：镜像质量

- 优先级：Must
- 要求：API使用多阶段构建、明确版本的基础镜像和`.dockerignore`，最终镜像不包含Go编译缓存、Git目录和测试数据。
- 验收：镜像能够独立启动，镜像检查中不存在无关源码和密钥。

### NFR-008：可观测性

- 优先级：Must
- 要求：关键组件具有可识别的健康状态和结构化日志；API错误应附带request ID以便关联排查。
- 验收：能够从一次失败HTTP请求追踪到对应错误日志。

### NFR-009：可维护性

- 优先级：Must
- 要求：Go代码按职责组织，Handler不直接承载复杂数据库查询和业务规则；公共错误、配置和日志行为保持一致。
- 验收：架构评审和代码评审中不存在全部逻辑堆积在`main.go`或单一Handler文件的情况。

### NFR-010：可重复部署

- 优先级：Must
- 要求：所有依赖镜像使用固定版本，部署步骤、环境变量和代理注意事项有文档记录。
- 验收：在第二个干净环境中仅依据README和部署文档能够完成启动和基本查询。

## 9. 数据需求

### 9.1 日志记录必要字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 是 | SQLite内部主键 |
| `event_id` | 是 | 稳定幂等键，全表唯一 |
| `source_event_id` | 否 | 来源服务提供的事件标识，不直接作为全局唯一键 |
| `container_name` | 是 | 来源容器名 |
| `container_id` | 否 | Docker容器ID |
| `service` | 是 | 逻辑服务名 |
| `level` | 是 | 大写规范化级别，未知时为`UNKNOWN` |
| `message` | 是 | 日志正文 |
| `source` | 是 | `stdout`、`stderr`或`file` |
| `log_path` | 否 | 文件来源路径 |
| `log_offset` | 否 | 来源文件偏移量 |
| `logged_at` | 是 | 日志发生时间，UTC |
| `ingested_at` | 是 | 平台入库时间，UTC |
| `raw_event` | 否 | 原始事件JSON，用于排查 |

### 9.2 数据完整性

- `event_id`必须建立唯一约束。
- 必要字段不得为NULL或空字符串。
- `logged_at`和`ingested_at`必须可用于时间范围查询。
- 原始事件保存失败不得破坏已经规范化的必要字段。
- 数据库迁移必须可重复执行，服务重启不得重复创建或破坏表结构。

### 9.3 查询索引目标

数据结构至少应支持以下访问模式：

- 按`event_id`去重。
- 按`container_name + level + logged_at`组合过滤。
- 按`service + logged_at`过滤和统计。
- 按`logged_at`倒序分页。

具体索引由架构设计确定，并通过查询计划或性能测试验证有效性。

## 10. API通用要求

### 10.1 成功响应

列表接口应返回稳定的JSON结构，包括：

- `data`：数组，允许为空。
- `pagination`：页码、每页条数和总数。
- `request_id`：本次请求标识。

详情和统计接口可使用不同的`data`对象，但必须保留`request_id`。

### 10.2 错误响应

错误响应应至少包含：

```json
{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "start must not be later than end"
  },
  "request_id": "example-request-id"
}
```

### 10.3 状态码

| 场景 | HTTP状态码 |
|---|---:|
| 查询或接收成功 | 200或201 |
| 参数、JSON或时间格式错误 | 400 |
| 日志ID不存在 | 404 |
| 请求体超过限制 | 413 |
| 请求过于频繁，若后续实现限流 | 429 |
| 未预期服务错误 | 500 |
| 服务尚未就绪 | 503 |

### 10.4 兼容性

- 公开接口使用`/api/v1`版本前缀。
- 内部接口使用`/internal/v1`版本前缀。
- v1 API稳定后，现有字段不得在同一v1版本中无说明删除或改变含义。

## 11. 验收测试基线

### AT-001：正常端到端采集

1. 从干净环境启动Compose。
2. 生成1000条具有唯一`source_event_id`的日志，覆盖stdout、stderr和文件来源。
3. 等待采集完成。
4. 验证SQLite总记录数和唯一`event_id`数均为1000。
5. 抽查三类来源的容器、服务、级别和时间字段。

通过条件：预期事件全部可通过公开API查询，缺失数为0、重复存储数为0。

### AT-002：下游中断恢复

1. 在正常链路基础上停止API或Logstash。
2. 继续生成200条唯一事件。
3. 恢复被停止的组件。
4. 等待积压事件完成投递。

通过条件：最终总记录数和唯一数均为1200，无需人工修改队列或registry。

### AT-003：采集器重启恢复

1. 确认前1200条事件已经入库。
2. 重启Filebeat。
3. 生成100条新事件。

通过条件：最终总记录数和唯一数均为1300，旧事件没有被重复存储。

### AT-004：组合查询

准备多个容器、服务、级别和时间范围的数据，分别执行单条件和组合条件查询。

通过条件：返回结果全部符合过滤条件、时间倒序正确、分页没有遗漏和重复、非法参数返回预期错误。

### AT-005：持久化

1. 记录当前数据总数。
2. 删除并重建`api`容器。
3. 再次查询数据。

通过条件：数据库文件仍存在，记录总数和内容不变。

### AT-006：启动时间

连续5次启动API并测量从进程启动到`/readyz`成功的时间。

通过条件：每次均不超过3秒，并在性能报告中保留原始结果。

### AT-007：查询性能

在10,000条数据、10并发、持续30秒条件下执行组合查询。

通过条件：p95不超过500ms且错误率为0；报告包含完整测试环境和命令。

### AT-008：一键部署

在干净环境中仅根据部署文档执行`docker compose up -d --build`。

通过条件：所有必需服务最终正常，公开API可访问，不需要容器内人工初始化。

### AT-009：优雅停机

在API处理请求时发送`SIGTERM`并观察退出行为与数据库状态。

通过条件：服务在配置超时内退出，数据库可再次打开，已确认事务没有产生半条记录。

### AT-010：结构化日志与request ID

1. 分别发起一次成功查询、一次非法参数查询和一次可控内部错误请求。
2. 记录每次响应中的request ID。
3. 检查对应的结构化请求日志和错误日志。

通过条件：响应和相关日志使用相同request ID；日志包含方法、路径、状态码和耗时；日志不完整输出用户正文及敏感Header。

### AT-011：自动化质量检查

1. 执行Go格式化检查、静态检查和`go test ./...`。
2. 生成核心包覆盖率报告。
3. 执行架构职责检查，确认Handler、Service和Repository边界没有被绕过。

通过条件：全部自动化检查通过，核心包覆盖率达到目标，代码结构符合已评审架构。

## 13. 优先级说明

- Must：MVP正式验收不可缺少，未通过则项目不能验收。
- Should：核心目标通过后应完成，但可在明确记录风险后延期。
- Could：时间允许时的增强项，不影响MVP验收。

本文档当前列出的FR和NFR均为Must。Nginx反向代理属于Could，不进入核心迭代的关键路径。

## 14. 待架构阶段细化事项

以下事项不会改变本需求基线，但必须在架构设计或ADR中给出明确结论：

7. 性能测试工具以及原始结果保存格式。
