# ADR-002：使用稳定事件指纹和SQLite唯一约束实现幂等存储

> 状态：Accepted
>
> 决策日期：2026-07-22
>
> 适用版本：v0.1.0

## 1. 背景

Filebeat和Logstash组成的日志传输链路按至少一次语义工作。以下场景都可能使同一事件再次到达API：

- Logstash已经把请求发送给API，但在收到响应前连接中断。
- API已经提交SQLite事务，但响应未能返回。
- Filebeat或Logstash在确认状态持久化前重启。
- 运维者手工重放一个批次。

如果只使用SQLite自增ID，每次重试都会创建新记录，最终查询和统计将出现重复。因此必须为同一来源事件计算稳定幂等键，并在数据库层建立唯一约束。

## 2. 决策驱动因素

- 同一事件重复提交时最终只保存一次。
- 不要求所有来源应用都预先生成`source_event_id`。
- 事件指纹在Filebeat、Logstash和API重试期间保持稳定。
- 不依赖进程内存状态，API重启后仍然有效。
- 批量写入时不逐条执行“先查再插”。
- 算法可以测试、版本化和解释。
- 极低碰撞概率，且冲突行为由数据库原子保证。

## 3. 已考虑方案

### 方案A：只使用SQLite自增ID

结论：不采用。

自增ID只能标识数据库记录，不能识别两次请求是否来自同一日志事件。

### 方案B：只信任来源提供的source_event_id

优点：实现简单，测试生产者可以生成明确编号。

缺点：普通容器stdout日志通常没有`source_event_id`；不同服务可能使用相同编号；恶意或错误来源可能大量复用ID。

结论：来源ID作为指纹输入，但不直接作为全局唯一键。

### 方案C：只对message做哈希

结论：不采用。

同一服务在不同时间产生相同正文是正常情况，只对正文哈希会错误合并真实事件。

### 方案D：在API收到事件时生成随机UUID

结论：不采用。

同一事件重试时会生成不同UUID，无法去重。

### 方案E：稳定来源字段规范化后计算SHA-256，并建立唯一索引

优点：

- 无需来源必须提供全局ID。
- 重试期间输入字段保持不变，结果稳定。
- SHA-256碰撞概率可忽略。
- 可以通过算法版本前缀演进。
- 数据库唯一约束提供并发原子性。

缺点：

- 必须严格定义规范化字段和编码方式。
- 来源元数据不足时存在错误合并风险。
- 算法变更需要兼容旧数据。

结论：采用。

## 4. 决策

数据库`logs.event_id`保存平台生成的全局幂等键，而不是直接保存来源原始ID。

event ID格式：

```text
v1:<64位小写SHA-256十六进制摘要>
```

API使用固定字段顺序的Go结构体生成规范JSON，再对JSON字节计算SHA-256。不得对map直接依赖未明确的业务字段集合，也不得使用字符串简单拼接造成分隔符歧义。

## 5. v1指纹输入

### 5.1 来源提供source_event_id时

`source_event_id`必须在同一逻辑服务内稳定且唯一。平台使用服务名作为命名空间，因此同一来源事件即使因容器重建而由新的容器实例重放，仍会得到相同平台`event_id`。

规范输入：

```json
{
  "version": "v1",
  "service": "log-producer",
  "source_event_id": "event-000001"
}
```

这样不同服务使用相同来源编号时不会产生全局冲突，同一服务重放相同来源事件时则能够正确去重。

### 5.2 来源没有source_event_id时

规范输入至少包括：

```json
{
  "version": "v1",
  "agent_id": "filebeat-agent-id",
  "container_id": "example-container-id",
  "source": "stdout",
  "log_path": "/var/lib/docker/containers/.../...-json.log",
  "log_offset": 12345,
  "logged_at": "2026-07-22T08:00:00.123456789Z",
  "message": "example log message"
}
```

字段意义：

- `agent_id`区分不同采集器身份。
- `container_id`区分容器实例。
- `source`区分stdout、stderr和文件来源。
- `log_path + log_offset`标识来源流中的位置。
- `logged_at + message`在轮转或元数据不完整时提供额外区分。

具体DTO字段名可以与Filebeat原始字段不同，但进入指纹前的语义和顺序必须由测试固定。

## 6. 规范化规则

计算哈希前必须：

1. 时间转换为UTC并使用RFC3339Nano。
2. `source`转换为约定小写值。
3. 容器ID和来源ID去除首尾空白，但不随意改变内部字符。
4. 日志正文保留原始有效内容，不进行会把两个不同事件变成相同值的模糊清洗。
5. 缺失可选字段编码为确定的空字符串或零值。
6. 使用固定Go结构体和`json.Marshal`产生稳定字段顺序。
7. 哈希算法固定为SHA-256。
8. 最终加上`v1:`前缀。

## 7. 数据库约束

`logs`表必须包含：

```text
event_id TEXT NOT NULL UNIQUE
```

GORM迁移必须创建唯一索引。应用启动后的就绪检查或集成测试应验证唯一约束存在，不能只依赖Go代码先查询。

原因：两个并发请求可能同时执行“未查询到记录”，只有数据库唯一约束才能原子阻止重复插入。

## 8. 批量写入策略

批量接收流程：

1. 校验并规范化所有可处理事件。
2. 为每个事件计算平台`event_id`。
3. 在短事务中批量插入。
4. 使用SQLite冲突忽略语义处理`event_id`冲突。
5. 根据合法事件数与实际插入数计算重复数量。
6. 提交事务后才向Logstash返回成功。

逻辑目标等价于：

```sql
INSERT INTO logs (...)
VALUES (...)
ON CONFLICT(event_id) DO NOTHING;
```

实际实现使用GORM的冲突子句，不手工拼接包含用户数据的SQL。

## 9. 批次结果语义

```text
received = 请求中事件总数
inserted = 本次新插入数量
duplicated = 合法但event_id已存在的数量
rejected = 永久不合法且未尝试入库的数量
```

必须满足：

```text
received = inserted + duplicated + rejected
```

如果数据库事务整体失败，则不得返回上述成功计数；API返回可重试错误，Logstash重新投递整个批次。

## 10. 并发与事务

- 去重正确性由SQLite唯一索引保证，不由进程内map保证。
- 进程内map可以作为单批次优化，但不是事实来源。
- 批量事务只包含数据库操作，不包含HTTP调用和日志传输。
- 如果事务失败，整个待写入集合回滚。
- 重试同一批次后，已经在更早成功事务中存在的事件被计为重复，不会再次写入。

## 11. API行为

### 11.1 重复事件

- 重复不是服务器错误。
- 单条重复请求返回成功并说明未新增。
- 批量重复计入`duplicated`。
- 不因重复返回5xx，避免Logstash无限重试。

### 11.2 永久非法事件

- 在计算event ID前完成必要字段和大小校验。
- 永久非法事件计入`rejected`并记录有限错误摘要。
- 不把无法解析的整批请求伪装成成功。

### 11.3 暂时性数据库错误

- 返回503或500等可重试状态。
- 不返回虚假的inserted计数。
- 结构化错误日志包含request ID。

## 12. 正面影响

- Logstash安全重试POST不会造成SQLite重复数据。
- API重启不影响去重状态。
- 多API实例并发写入时仍由数据库原子约束保证一致性。
- 测试可以使用明确来源ID，同时平台也能处理普通stdout日志。
- 算法前缀允许未来保留v1数据并引入v2。

## 13. 负面影响与限制

- 计算SHA-256增加少量CPU开销。
- 需要保留足够稳定的Filebeat来源元数据。
- 如果来源元数据严重缺失，两个真实事件存在被错误合并的可能。
- 指纹字段改变会使同一原始事件产生不同版本ID。
- 当前去重是永久唯一；若未来需要允许同一事件在不同租户存在，必须把租户加入指纹。

## 14. 风险缓解

- Filebeat和Logstash映射测试验证指纹字段不会在重试中变化。
- 对有来源ID和无来源ID两条路径分别编写表驱动测试。
- 用数据库并发集成测试验证唯一约束。
- 将算法输入结构和黄金哈希结果固定在测试用例中。
- 在`event_id`中保留版本前缀，禁止静默改变v1算法。
- 原始来源事件ID作为普通字段或`raw_event`的一部分保留，便于排查。

## 15. 必需测试

### 15.1 稳定性

同一规范事件计算100次，必须得到完全相同的v1哈希。

### 15.2 区分性

以下任一稳定身份字段改变时，应得到不同哈希：

- 服务名。
- 容器ID。
- 来源event ID。
- 文件偏移量。
- 日志发生时间。
- 日志正文。

测试应根据两条指纹路径选择实际适用字段。

### 15.3 重复单条

同一事件连续提交10次，SQLite只保存一条。

### 15.4 重复批次

同一100条批次提交两次，第一次`inserted=100`，第二次`duplicated=100`，最终总数100。

### 15.5 并发重复

多个goroutine并发提交同一事件，最终SQLite只保存一条，其他请求得到重复结果或成功冲突忽略。

### 15.6 重启后重复

API重启后重新提交旧批次，SQLite仍然不新增重复记录。

### 15.7 事务失败

模拟数据库写入失败，API不返回成功计数；恢复后重试能够完整写入。

## 16. 重新评估条件

以下情况需要新增ADR，而不是直接修改v1算法：

- 引入多租户。
- 日志来源不再提供稳定文件位置或偏移量。
- 存储从SQLite迁移到其他具有不同冲突语义的系统。
- 需要基于有限保留窗口而不是永久去重。
- 发现v1字段无法区分合法的高频相同事件。
- 需要跨集群全局去重。
